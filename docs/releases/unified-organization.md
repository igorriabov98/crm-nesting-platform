# Пользователи, структура и доступ CRM

## Состав изменения

Единый адрес `/admin/organization` содержит пользователей, отделы, дерево структуры и должности. Старые адреса перенаправляют на нужную вкладку. Кадровые таблицы `employees` не переносятся. Карточка пользователя показывает все назначения, основное назначение, фактические права, историю и передачу дел. Основное назначение не влияет на права.

Матрица остаётся в `/admin/settings/access`. Сохранение отправляет только изменённые строки с ожидаемой версией, показывает затронутых пользователей и отклоняет конфликт. Обновление данных сохраняет черновик. Предварительный просмотр прав не меняет сессию; вход от лица пользователя — отдельное действие. На складе право просмотра сохраняет таблицу и историю, а формы прихода, корректировки, удаления и перевода остатков доступны только при действующем праве управления.

Административный статус хранится в `user_system_roles`, независимо от должности и отдела. Он переносится только для пользователей, которых действующий SQL evaluator уже признаёт администраторами. Изменение статуса доступно другому активному администратору; последний администратор защищён. Блокировка требует предварительного снятия административного статуса.

Руководство определяется флагами назначений. Зеркало `departments.head_user_id` синхронизируется транзакционно. Несколько назначений одного руководителя сохраняются; значения head/member не угадываются и не меняются при переносе. Прямые записи authenticated в пользователей, назначения, отделы, должности и матрицу закрыты; изменения проходят через проверяемые RPC с версией и аудитом.

97 защищённых страниц проверяют доступ до загрузки своих данных. Оболочка обновляет снимок при переходе, возвращении во вкладку и явном изменении доступа; ответы прежних запросов отбрасываются. Ошибка проверки, загрузка и запрет отображаются отдельно. Таймауты Auth и HTTP 429 не превращаются в подтверждённый отказ или выход из сессии. Черновик матрицы переживает перепроверку; скрываются также диалоги, отрисованные через портал.

## Миграции

Одной транзакцией с блокировкой записей организации и атомарной записью ledger применяются девять файлов `20260919120000`–`20260919125500`:

1. Защищённые полномочия, версии, первичные назначения, аудит и проверки переноса.
2. Единый evaluator, снимок доступа и сохранение матрицы с CAS.
3. Перевод существующих SQL-проверок администратора на защищённый статус.
4. Атомарные команды структуры и согласование руководителей.
5. Реестр обязанностей, передача, блокировка и очередь синхронизации Auth.
6. Согласованный снимок организации.
7. Аренда задания синхронизации Auth и защита от запоздавших ответов.
8. Отдельное согласованное изменение: Финансовый отдел, head/member, `inventory` view=true/manage=false; остальные области действия сохраняются.
9. Оставшиеся административные проверки RLS и обязательная активность аккаунта. Для product-files сохраняется существующий набор допущенных системных ролей; защищённый администратор получает доступ независимо от роли. Старые отозванные функции ролей в этих политиках заменены активным проверяемым helper.

Миграции останавливаются при неоднозначном руководстве, циклах, отсутствии подтверждённого администратора, изменении объединения прав head/member либо неоднозначном Финансовом отделе. Несколько назначений без основного и неоднозначное старое подчинение сохраняются для адресного решения администратором.

## Передача дел

Мастер показывает задачи, ожидающие делегирования, руководящие назначения, подчинённых, клиентов, запросы отделов, финансовые обязательства, совещания, проекты и специальные обязанности по заявкам/ревизиям. Реестр расположен в `private.organization_obligation_sources`.

Передаются поддерживаемые обязанности и связанные незавершённые задачи; преемник должен быть активным и иметь необходимые права. Назначение ответственного за компанию сохраняет правило активного менеджера Sales и отдельную административную проверку. Специальные согласования требуют штатного процесса и блокируют завершение мастера. Завершённые решения и авторство сохраняются.

Каждая передача имеет ключ идемпотентности и отпечаток проверенного объекта. Частично выполненные передачи показываются явно. Финальная блокировка повторно проверяет зависимости под общей блокировкой, с которой согласованы триггеры назначения обязанностей. Появление новой обязанности предотвращает блокировку; последующее назначение заблокированному аккаунту отклоняется.

CRM закрывает доступ сразу. Auth ban/unban синхронизируется отдельной устойчивой очередью `user_auth_sync`, через отдельный защищённый cron `/api/organization/auth-sync` каждые пять минут (Vercel Pro, `CRON_SECRET`); существующий `/api/tasks/due` также может обработать очередь. Неудача Auth не возвращает права CRM; состояние ожидания видно в карточке. Уже выданные JWT не обходят проверку активности/RLS. Срок действия ранее выданных подписанных URL не изменяется этой миграцией.

## Локальная проверка

Все команды БД должны явно указывать выделенную одноразовую **локальную** тестовую базу. Полный replay пересоздаёт её. Нельзя подставлять production/staging или общую БД с нужными данными.

```sh
npm run test:organization
FULL_SCHEMA_TEST_DATABASE_URL=postgresql://localhost/crm_unified_organization_test node scripts/test-technologist-request-financial-approval-db.mjs
ORGANIZATION_TEST_DATABASE_URL=postgresql://localhost/crm_unified_organization_test npm run test:organization:db
npm run test:organization:migration
FULL_SCHEMA_TEST_DATABASE_URL=postgresql://localhost/crm_unified_organization_test node scripts/test-order-discounts-db.mjs
```

Миграционная репетиция создаёт собственные БД, проходит перенос с сохранением идентификаторов и прав, восстанавливает полный pg_dump в отдельную БД и сравнивает пользователей, назначения и матрицу. Тест гонок работает с собственной копией явно указанной тестовой базы. Тесты свойств выполняют свои изменения в транзакции с ROLLBACK.

Синтетический интерфейс без production-реквизитов: `npx tsx scripts/organization-ui-fixture.ts`, затем `http://127.0.0.1:4319/session`. Для сотрудника Финансового отдела — `/session?user=employee`. Это макет ответов Supabase для проверки навигации/состояний; запись CRM на нём отклоняется. `/control` включает ошибку чтения прав. Проверка настоящих RPC/RLS выполняется отдельными SQL-тестами, а не этим стендом. Для Финансового отдела проверены обычный переход, обновление, назад/вперёд и отсутствие формы прихода. Отдельный тест настоящего компонента с заполненной строкой склада проверяет отсутствие кнопок изменения при просмотре и после отзыва управления, а также их наличие у управляющего складом.

Подтверждённые проверки: типизация и production build; проверки 64 ресурсов/маршрутов; объединение назначений и неизменность прав при выборе основного; отсутствие выдачи админства по названию должности; защита последнего администратора; CAS; циклы; архивирование; идемпотентная передача; гонки блокировки/новых обязанностей; устаревший ответ Auth; RLS просмотра склада без записи для финансов; отсутствие доступа заблокированного JWT; финансовое согласование и конкурентное решение; коммерческая видимость/прайсы/скидки; сценарии снабжения.

В общем ESLint остались восемь существовавших на базовом HEAD замечаний `react-hooks/error-boundaries` в двух страницах nesting. Сравнение с базовым содержимым подтвердило, что они не внесены этой работой. Остальные изменённые TS/TSX проходят ESLint.

## Порядок выпуска

1. Получить отдельное разрешение на push, миграции и deploy по `AGENTS.md`. Подготовленный код не означает разрешение менять production.
2. Получить доступ для чтения SQL production, подтвердить SHA приложения и migration ledger. Прямое подключение из окружения Railway проверено 19 сентября 2026: 22 аккаунта, 13 активных, 10 отделов; расхождений прав перед переносом нет. Выгрузка Vercel не возвращает значение защищённого service-role ключа; это не признак неисправности production.
3. Запустить `ORGANIZATION_DATABASE_URL=... npm run ops:organization:preflight -- /защищённый/путь/before.json`. Значение подключения не выводится. Снимок содержит персональные данные и создаётся с правами 0600; его нельзя включать в git. Скрипт работает только на чтение и завершится кодом 2 при расхождениях, препятствующих выпуску.
4. Разобрать решения по каждому пользователю/отделу. Не угадывать администратора по названию должности. Помимо модульных разрешений проверить изменения областей заводов/компаний. Повторить снимок при приостановленных изменениях организации, чтобы набор данных был согласованным.
5. Подтвердить свежую полную резервную копию (public, auth, storage metadata и migration ledger), время, место хранения и успешную репетицию восстановления. Снимок JSON не заменяет резервную копию БД или файлов.
6. PR → CI → единственный merge в свежий main. Это согласованный переход приложения и схемы: старое приложение использует прежний RPC матрицы и прямые записи структуры, которые закрываются миграцией. На окно переноса остановить изменения/фоновые процессы, которые затрагивают организацию, и не оставлять старое приложение обслуживать пользователей после SQL-перехода.
7. Применить только отсутствующие миграции через ledger, затем выпустить приложение из main. Проверить `/api/version`, записи ledger, состояние cron и очереди Auth. Railway и параметры deployment workflow — по согласованному оператором объёму выпуска.
8. Снять after-снимок и сравнить каждого пользователя/ресурс с before. Допустим только согласованный просмотр склада Финансовым отделом и адресно утверждённые решения. Другие расхождения блокируют открытие системы.
9. На действующей сессии Виктории проверить склад: переход из меню, прямая ссылка, обновление, назад/вперёд, восстановление сессии. Отдельно подтвердить отсутствие кнопок изменения и серверный/RLS запрет записи без реального изменения остатков. Проверить администратора после смены назначения на тестовой копии реальных данных. Production UI-проверки — только чтение.

## Восстановление

Простое возвращение старого приложения после миграции небезопасно: старые проверки снова зависят от должностей и ожидают прежние контракты записи. При отказе выпуска сохранить журнал/очередь и остановить записи, затем использовать согласованный rollback приложения **вместе с восстановлением подтверждённой полной копии БД**. Новые операции после копии требуют отдельного разбора, их нельзя молча потерять. Состояние Auth ban/unban должно быть сверено с восстановленной активностью аккаунтов; старый процесс очереди перед восстановлением останавливается. Восстановление production требует отдельного разрешения.

## Инцидент локального тестирования

Один запуск регрессионного скрипта без явного URL пересоздал общую локальную `crm_full_schema_test`; предыдущее состояние не было сохранено. Production не затронут. Скрипты полного replay и финансового согласования теперь отказываются запускаться без `FULL_SCHEMA_TEST_DATABASE_URL`; дальнейшие проверки выполнялись в выделенной базе этой задачи.

## Репетиция на реальных данных перед выпуском

19 сентября 2026 создан полный архив pg_dump PostgreSQL 17 (SHA256 `8a6ec7dab07c1be87bfa0c03b4b048b103a5d6c2ebfe249195eb34d008df5f9d`). Архив и снимки находятся в защищённом локальном каталоге оператора, вне git и публичных артефактов CI. Восстановление public, auth и storage metadata проверено в отдельном локальном PostgreSQL 17; служебные объекты расширений Supabase cron/net/vault исключены из локального восстановления, но сохранены в полном архиве. Восстановление этих расширений требует совместимого Supabase-окружения. Файлы Storage в этой работе не изменяются.

Данные организации совпали со снимком, включая время после нормализации часового пояса. После миграций идентификаторы и набор администраторов сохранены. Единственное изменение фактических разрешений — согласованный просмотр склада Финансовым отделом без управления. Пять неоднозначных назначений/связей оставлены для адресного решения без изменения прав.
