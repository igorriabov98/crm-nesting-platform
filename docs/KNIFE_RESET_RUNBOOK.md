# Полный сброс данных ножей

Этот runbook относится только к отдельно подтверждаемому необратимому сбросу.
Он не запускается миграцией, `deploy.yml`, сборкой или тестами. Резервная копия
по зафиксированному решению не создаётся: до `COMMIT` действует rollback, после
`COMMIT` данные БД восстановить нельзя.

## 1. Совместимый релиз

Сначала отдельно развернуть код и миграцию
`20260825170000_knife_profile_without_standard_length.sql`. Убедиться, что SHA
Railway и Vercel совпадает с `main`. Сам сброс на этом этапе не запускать.

## 2. Read-only preflight

Сценарий использует только временные таблицы и завершает транзакцию `ROLLBACK`:

```sh
psql "$SUPABASE_DB_URL" -X -v ON_ERROR_STOP=1 \
  -f scripts/knife-reset-preflight.sql
```

Сохранить `expected_fingerprint`, полный JSON количеств и список storage-файлов.
Сценарий прервётся при неизвестной внешней или полиморфной зависимости.

## 3. Отдельное подтверждение количеств

Оператор должен явно подтвердить именно показанные preflight количества,
необратимость без резервной копии и production-среду. После подтверждения не
создавать и не менять заявки, ножевой склад, поставки или карты раскроя до
завершения транзакции.

## 4. Транзакционный сброс

Подставить UUID оператора и fingerprint без изменения текста подтверждения:

```sh
psql "$SUPABASE_DB_URL" -X -v ON_ERROR_STOP=1 \
  -v actor_id='00000000-0000-0000-0000-000000000000' \
  -v expected_fingerprint='00000000000000000000000000000000' \
  -v confirm='DELETE_ALL_KNIFE_DATA_WITHOUT_BACKUP' \
  -f scripts/knife-reset-execute.sql
```

Сценарий берёт advisory/table locks, повторно строит scope и сравнивает
fingerprint. Любая ошибка откатывает все изменения. Активные брони возвращаются
штатной функцией до удаления. Машины и самостоятельные производственные факты
сохраняются; удаляются только связи уничтожаемых заявок, после чего статусы и
фактическая дата материала пересчитываются.

## 5. Файлы после COMMIT

Сначала выполнить dry-run очереди с тем же fingerprint:

```sh
npm run ops:knife-reset:cleanup -- \
  --fingerprint=00000000000000000000000000000000
```

Удаление Supabase Storage и архивной копии Google Drive требует отдельного
подтверждения production-удаления:

```sh
npm run ops:knife-reset:cleanup -- \
  --fingerprint=00000000000000000000000000000000 \
  --execute \
  --confirm=DELETE_KNIFE_RESET_STORAGE_OBJECTS
```

Неудачные файлы получают статус `failed` и остаются повторяемыми. Повторный
запуск с тем же fingerprint обрабатывает `pending` и `failed`, не откатывая БД.

## 6. Контроль после операции

- Повторный preflight должен остановиться с нулевым набором для удаления.
- В каталоге и на складе не должно быть категории `knives`.
- Новая попытка записать нож с `standard_length_mm` должна отклоняться.
- Проверить фактические даты материала и статусы затронутых машин.
- Проверить счётчики заявок, снабжения и задач после перезагрузки приложения.
- Любой production smoke с созданием ножа или складского движения требует
  отдельного разрешения.
